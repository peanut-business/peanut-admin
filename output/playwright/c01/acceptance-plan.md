# C01 文章分类双系统最低充分验收计划

> 目标：用一组隔离夹具和一条连续状态流覆盖 `C01-01`～`C01-10`，不为单个编号重复建数、重复登录或重复验收同一行为。  
> 系统：LikeAdmin 1.9.4 与 Peanut Admin。
> 状态：已执行完成；C01-01～C01-10 均已取得最低充分证据，双端夹具已精确清理。  
> 契约：`docs/likeadmin-article-category-contract.md`。

LikeAdmin 页面结构先在 `reference-runtime/` 完成一次真实浏览器只读观察；随后正式验收按本文的共享夹具连续状态流执行完成。运行结果确认 LikeAdmin 连续两次 `append()` 时后一次覆盖前一次，因此列表实际只附加 `article_count`，不返回 `is_show_desc`；本文执行前的对应预期已由最终运行契约取代，不得据此重复验收。

权限决策已冻结：Peanut 只补登记缺失的写接口 `edit`；共享只读 `all` 与 LikeAdmin 一样不建立权限节点，任何已登录管理员在两端均可调用。

## 1. 唯一运行标识

本轮只允许使用以下一组标识；重试也不得更换前缀或另建平行夹具：

```text
RUN  = 26080101
PFX  = C0126080101
```

派生名称：

```text
分类 A 初始名   C0126080101-A
分类 A 编辑名   C0126080101-A2
分类 B          C0126080101-B
分类 C          C0126080101-C
文章             C0126080101-ART
普通管理员       c01op26080101
普通角色         C01R26080101
越权探针不存在ID 2147483001
无命中筛选值     C0126080101-NOT-MATCH
```

91 字符名称由执行脚本基于 `PFX + '-LONG-'` 补齐，并在发送请求前只断言一次 `mb_strlen=91`。不得手工复制一个无法证明长度的字符串。

两套系统使用相同业务值但各自独立记录实际主键。任何清理和数据库断言都使用“实际主键 + PFX/账号/角色名”双重条件，不假定两端自增 ID 相同。

## 2. 共享夹具

每端只建立以下业务夹具：

| 夹具 | 建立方式 | 初始值 | 合并覆盖目的 |
|---|---|---|---|
| 分类 A | root API 新增，省略 `sort` | name=A，is_show=1，sort 应落 0 | add 默认值；随后复用为 detail/edit/最高排序分类 |
| 分类 B | root 真实页面新增 | name=B，sort=9000，is_show=1 | 真实新增路径；与 C 同 sort 验证 id 倒序 |
| 分类 C | root API 新增，创建顺序晚于 B | name=C，sort=9000，is_show=1 | 文章计数、状态消费、占用删除、软删除 |
| 文章 ART | root 既有文章新增能力 | cid=C，is_show=1，sort=0 | 只作为 C01 关联夹具，不验收 C02 字段 |
| 普通角色 | root 权限管理 | 分类父菜单、页面及按钮权限 | 一次授权→撤权→恢复权限流 |
| 普通管理员 | root 管理员能力 | 绑定上述角色 | 菜单、按钮、直达、API 权限 |

分类 A 创建后通过唯一一次编辑改为：

```text
name=C0126080101-A2
sort=9001
is_show=1
```

此后默认顺序应同时证明：

```text
A2(sort=9001) → C(sort=9000, newer id) → B(sort=9000, older id)
```

这一个顺序同时覆盖“数值越大越前”和“同 sort 时 id DESC”，不另建排序夹具。

## 3. 基线快照

任何写请求前，每端各执行一次只读联合基线快照并保存到：

```text
output/playwright/c01/baseline/likeadmin.json
output/playwright/c01/baseline/peanut.json
```

快照至少包含：

1. 当前数据库连接身份、host、port、database、服务端 hostname；
2. 分类表中 `name LIKE 'C0126080101%'` 的物理行（包括软删除行）计数，应为 0；
3. 文章表中 `title='C0126080101-ART'` 的物理行计数，应为 0；
4. 管理员 `c01op26080101`、角色 `C01R26080101`、角色菜单、管理员角色、会话的计数，应为 0；
5. 与临时账号精确匹配的操作日志和未认证登录日志计数；
6. 当前活动分类/文章的总数和 ID 摘要，用于证明失败请求未影响非夹具数据；
7. C01 权威菜单及权限字符快照：
   - LikeAdmin 保留菜单 `70,73,78,79,80,81`，并记录 `edit/all` 未登记；
   - Peanut 从当前迁移和数据库读取实际菜单 ID，不预设 ID；应登记 `lists/add/edit/delete/detail/updateStatus`，不应存在 `all` 权限节点；
   - 记录 `server/database/init.sql` 的全局菜单 ID 唯一性和 C01 幂等迁移状态；此前发现的跨域 ID 冲突由主线修复，但在静态检查、迁移和运行证据齐全前不得记为通过；
8. 当前未结束数据库事务摘要；
9. 两端现有认证缓存目标只记录 key/path 摘要，不把 token 内容写入证据。

基线只做一次。后续各阶段只对夹具主键和业务不变量做增量快照，不重复全库盘点。

## 4. 执行总序

```text
基线
  → root 建共享夹具
  → 一次 root 页面主流程
  → 最少 API 边界矩阵
  → 一次分类停用消费闭环
  → 一次普通角色授权/撤权/恢复
  → 一次占用删除→文章软删→分类软删
  → 一次联合不变量审计
  → 一次双端精确清理与联合零计数
```

必须严格按此顺序执行。后序步骤复用前序状态，不恢复后重新建一套夹具。

## 5. 阶段 A：建立夹具与 root 页面主流程

### A1. root 会话

- 复用两套系统现有 root 会话；只有会话失效时才各登录一次。
- 打开文章栏目页并开启网络记录和浏览器快照。
- LikeAdmin 页面入口为“文章资讯 → 文章栏目”；Peanut 使用其对齐后的对应入口。

### A2. 建立三条分类和一篇文章

按固定顺序：

1. API 新增 A，省略 `sort`；只读核对实际 `sort=0`。
2. 真实页面新增 B，`sort=9000,is_show=1`。
3. API 新增 C，`sort=9000,is_show=1`，确保 C 的 ID 晚于 B。
4. 使用既有文章新增能力创建 ART 并绑定 C；只核对 `cid/is_show/delete_time`，不扩展到 C02 内容验收。

### A3. 唯一详情/编辑路径

在真实页面点击 A 的“编辑”：

1. 捕获唯一一次 detail 请求和回显；
2. 修改为 A2、sort=9001、is_show=1；
3. 只提交一次；
4. 页面刷新后的同一列表作为 C01-01/C01-04/C01-07 的共同证据。

该列表必须一次证明：

- 字段包含名称、文章数、状态、排序和操作；
- A2 → C → B；
- C 的 `article_count=1`，A2/B 为 0；
- 页面没有父级、子分类、树展开或移动节点操作；
- 响应包含 `is_show_desc` 和 `extend=[]`。

不得为字段、文章数和排序分别再次刷新页面。

## 6. 阶段 B：最少 API 边界矩阵

同一 root token 下，每端按表执行一次。除表中请求外，不补“保险请求”。

### B1. 列表、分页、无筛选和导出

| 请求 | 预期 | 覆盖 |
|---|---|---|
| `GET lists?page_no=1&page_size=2` | count 与基线列表一致；夹具顺序 A2、C | 分页第一页、默认顺序 |
| `GET lists?page_no=2&page_size=2&name=C0126080101-NOT-MATCH` | count 与上一请求相同；name 被忽略；夹具 B 按全局位置出现 | 分页第二页、无业务筛选 |
| `GET lists?export=1` | `该列表不支持导出` | 禁止导出 |

若现有非夹具数据改变 B 在第二页的绝对位置，以 A2/C/B 三者的响应相对顺序和相同 count 为准；不得为了制造页码结果修改非夹具 sort。执行前若权威总数据使 `page_size=2` 无法覆盖 B，则仅把两请求的 `page_size` 调整为能形成两页的最小值，并在证据中记录一次计算，不能改夹具或重复试页码。

### B2. 新增验证

以下四个失败请求每端各一次：

| 请求 | 预期 |
|---|---|
| 缺 `name`，其他字段有效 | `资讯分类不能为空` |
| 91 字符 `name` | `资讯分类长度须在1-90位字符` |
| `sort=-1` | `排序值不正确` |
| `is_show=2` | LikeAdmin 运行时原文先固化；Peanut 业务语义同为拒绝 |

四个请求使用不会与 PFX 合法名称混淆的失败值，不产生新行。执行完四个请求后只做一次联合不变量快照，不为每个错误分别查库。

### B3. 不存在详情

```text
GET detail?id=2147483001
```

每端只请求一次，预期 `资讯分类不存在`。该请求同时证明 detail 的存在性校验，不再单独测试删除或状态的相同不存在校验。

## 7. 阶段 C：状态消费闭环

### C1. 唯一状态写

在 root 真实页面将 C 从 1 切换为 0，只操作一次。页面自动刷新后的同一响应必须证明：

- C 仍在管理列表；
- `is_show=0`；
- `is_show_desc=停用`；
- ART 和 `article_count=1` 未变化；
- 开关成功请求只更新 C，不更新文章。

不在本阶段恢复 C；后续删除约束直接复用停用状态。

### C2. 最少消费请求

每端只执行以下五个读取：

| 请求 | 预期 |
|---|---|
| 管理端 `GET articleCate/all` | 不含 C；仍含 A2/B |
| 移动端 `GET /api/article/cate` | 不含 C |
| PC `GET /api/pc/infoCenter` | 不含 C 分类块 |
| 移动端 `GET /api/article/lists?cid={C_ID}` | 仍含 ART |
| 移动端 `GET /api/article/detail?id={ART_ID}` | ART 仍可访问 |

这五个响应共同证明“分类入口隐藏，但不级联下线文章”。不得另做第二次状态切换或再次请求相同消费端。

## 8. 阶段 D：普通角色一次授权→撤权→恢复

权限流安排在 C 和 ART 仍存在时，使页面、读取和写入探针都有真实目标。

### D1. 建角色和管理员

- 创建角色 `C01R26080101` 与管理员 `c01op26080101`。
- LikeAdmin 授权其现有父菜单、分类页面及 `add/delete/detail/updateStatus`；安装 SQL无 `edit/all`，不得临时新增参考菜单伪造权限。
- Peanut 授权对齐后的父菜单、页面及 `add/edit/delete/detail/updateStatus`；不得创建或授予 `all` 权限节点。
- 记录实际角色关系 ID、管理员关系 ID、会话 ID 和真实认证缓存 path/key，后续只按这些精确恢复/删除。

### D2. 唯一授权态

普通管理员各登录一次并进入分类页：

- 菜单和分类页面可访问；
- add/delete/status 按钮可见；
- Peanut edit 按钮可见；
- LikeAdmin edit 按钮因权限漏登记而不可见，记录为参考缺陷，不重复验证；
- 同一页面的列表成功请求作为授权 API 证据，不再额外调用 lists。

### D3. 唯一撤权态

精确移除分类页面和全部分类按钮/API 权限关系，保留父级结构所需关系，失效当前管理员的真实认证缓存。刷新同一浏览器会话一次：

- 分类菜单消失；
- 直达分类路由不可用；
- 页面无 add/edit/delete/status 操作入口。

随后每端各执行一组且仅一组 API 探针：

| API | 无副作用请求 | LikeAdmin 预期 | Peanut 预期 |
|---|---|---|---|
| lists | 正常 GET | 权限不足 | 暂无访问权限 |
| add | 缺 name 的 POST | 权限不足先于验证 | 暂无访问权限先于验证 |
| detail | `id=A_ID` | 权限不足 | 暂无访问权限 |
| updateStatus | 发送 C 当前值 0 | 权限不足且不写 | 暂无访问权限且不写 |
| delete | `id=C_ID` | 权限不足且不进入占用校验 | 暂无访问权限且不写 |
| edit | 使用不存在 ID 2147483001 | **穿透到“资讯分类不存在”** | 暂无访问权限 |
| all | 正常 GET | **未登记放行** | **未登记放行** |

edit 使用不存在 ID，证明 LikeAdmin 绕过了权限中间件但不会修改业务数据。不得使用真实分类做同值更新，因为这会污染 `update_time` 和操作日志语义。

撤权探针后只做一次业务不变量快照，确认分类、文章和状态均未变化。两端 `all` 都是预期的登录后共享只读请求，不算业务副作用，也不应触发角色关系或缓存补丁。

### D4. 唯一恢复态

- 按记录的关系 ID/二元组精确恢复权限并失效真实权限缓存。
- 同一会话只刷新一次分类页，确认菜单、页面和 lists 恢复。
- 不重复逐个 API，也不再次检查 LikeAdmin edit 缺陷。

## 9. 阶段 E：占用删除与软删除

恢复 root 会话后，在 C 仍停用且 ART 仍活动的状态继续：

1. 真实页面删除 C 一次，预期：`资讯分类已使用，请先删除绑定该资讯分类的资讯`。
2. 一次不变量读取确认 C/ART 均未软删，C 状态仍 0，文章数仍 1。
3. 使用既有文章删除 API 软删 ART；这只是夹具状态准备，不展开 C02 验收。
4. 同一页面再次删除 C 一次，预期 `删除成功`。
5. 只做一次联合读取，证明：
   - 分类管理列表不再含 C；
   - detail(C_ID) 返回不存在；
   - all 不含 C；
   - C 和 ART 物理行存在但 `delete_time` 非空；
   - A2/B 仍活动；
   - 没有级联物理删除或修改其他文章。

这里的两个 delete 不是重复验收：第一次证明活动文章占用拒绝，第二次证明文章软删后分类软删成功，是同一状态流的两个必要分支。

## 10. 失败后统一不变量

以下失败请求共享一套数据库断言：四个新增验证、detail 不存在、撤权拒绝、越权 edit 不存在、占用删除。

失败请求之后不得出现：

- 额外 `PFX` 分类或文章；
- A2/B/C/ART 非预期字段、状态、sort、cid 或 `delete_time` 变化；
- 分类的意外物理删除；
- 文章级联停用、级联删除或 cid 变化；
- 新的分类父子关系或层级数据；
- 普通角色关系被业务请求改变；
- 未提交或悬挂的业务事务。

允许变化：

- 系统按既有规范新增操作/登录审计日志；
- 登录和权限缓存按授权流程更新；
- 正常读取不改变业务表。

每一组失败矩阵完成后只执行一次联合不变量查询。若出现意外失败，只允许再做一次只读诊断来确定直接原因，然后停止该分支并记录；不得换夹具、换路径或重复点击制造通过结果。

## 11. 阶段 F：联合审计

业务路径全部完成后、清理前，每端各做一次联合审计：

1. A2/B 活动，C/ART 已软删；
2. 所有 PFX 分类仍为扁平记录，不存在父级字段或外部层级关系；
3. 分类状态修改没有写入 ART 的 `is_show`；
4. 占用失败没有修改 C/ART；
5. C 只存在一条物理记录，ART 只存在一条物理记录；
6. 不存在同一次请求造成的重复分类或重复角色关系；
7. 权限关系已恢复到授权前记录的精确集合；
8. 无悬挂业务事务；
9. 非 PFX 分类、文章、管理员、角色和权威菜单摘要与基线一致。

该审计覆盖 C01-09，不为每条不变量另发一组请求。

## 12. 阶段 G：双端精确清理

### G1. 清理前解析精确目标

从执行证据中固化：

- A/B/C 分类实际 ID；
- ART 实际 ID；
- 临时管理员、角色、会话和关系实际 ID；
- 与临时账号/PFX 精确关联的操作日志和未认证登录日志 ID；
- 本轮真实权限缓存和 token 缓存精确路径/key。

任何没有被上述证据唯一确认的行、文件或缓存都不得进入清理范围。

### G2. 数据库事务顺序

每端各使用一个事务，按实际表结构和逻辑依赖执行：

```text
文章相关子表/收藏关系（仅 ART_ID）
  → ART 物理行
  → A/B/C 分类物理行
  → 临时管理员会话/组织关系/操作日志
  → 管理员角色关系
  → 临时角色菜单关系
  → 临时管理员
  → 临时角色
```

事务提交前必须断言每个删除计数等于已确认基线差值；任一计数不符即回滚，不扩大条件。

权威系统菜单不是夹具：

- LikeAdmin `70,73,78,79,80,81` 永不删除；
- Peanut 对应迁移菜单永不删除；其中只应新增 `edit` 写权限，不应存在 `all` 权限节点；
- 只删除临时角色与菜单的关系行。

### G3. 缓存

事务提交后只移除本轮临时管理员的真实权限缓存和 token 缓存。缓存是派生数据，可重建；不得清空应用全局缓存或其他管理员缓存。

### G4. 唯一联合零计数

提交后只执行一次联合零计数，并保存：

```text
output/playwright/c01/cleanup/likeadmin.json
output/playwright/c01/cleanup/peanut.json
```

目标全部应为 0：

```text
PFX categories (including soft-deleted physical rows)
ART physical row and its isolated child relations
temporary admin
temporary role
admin-role relation
role-menu relations
admin session
exact operation/login logs
temporary auth/token caches
```

同一联合查询中加入正向保护断言：

- LikeAdmin 权威菜单 `70,73,78,79,80,81` 数量仍为 6；
- Peanut 对应权威菜单数量与基线一致，`edit` 登记存在且 `all` 权限节点不存在；
- 非 PFX 分类/文章摘要与基线一致。

数据库物理删除只可从备份或已记录夹具 SQL 恢复；认证缓存可由系统重建。清理证据必须说明可恢复性和未触碰范围。
