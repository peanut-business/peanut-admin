## 1. 一句话定位

Peanut Admin 是一个可直接运行的多租户全栈管理系统脚手架，也提供可被其他项目单独安装的前端和后端核心包。

它先做到“像成熟 SaaS 后台一样能用”，再允许业务项目安装或开发商品、库存、销售、仓储等模块。

## 2. 先用一个真实例子说明

“甲公司”购买了系统，它是一个租户。甲公司有三个门店、两个仓库、多个部门和员工。

- 员工使用账号登录。
- 账号在甲公司内对应一个成员。
- 成员拥有角色、菜单权限、操作权限和数据权限。
- 甲公司开通“门店管理方案”和“仓储管理方案”。
- 两个方案都使用同一套商品和库存能力。
- 用户在门店页面销售商品时，销售模块调用库存模块扣减门店库存。
- 用户在仓库页面出库时，出库模块调用同一个库存模块扣减仓库库存。
- 库存只保存一份，不为门店系统和仓储系统各复制一套。

因此，门店管理和仓储管理可以是两个独立产品界面，但它们不是两套互不相识的数据模型。

## 4. 租户到底是什么

第一版统一使用 `Tenant`，不再同时用 `Organization` 表示同一层隔离边界。

租户通常是签约、付费、使用系统并拥有独立数据责任的经营组织。租户不是门店、仓库或供应商。一个租户可以同时管理多个类别、每类多个业务对象，例如多个门店、仓库、供应商和批发商，并拥有自己的部门和成员。

如果一家门店独立签约、独立管理账号、独立承担数据和账单，成为 Tenant 的仍是经营这家门店的公司或团队；该 Tenant 内再建立门店业务对象。不能把门店或仓库记录直接提升为 Tenant。

第一版不实现“集团租户下面再挂多个子租户”。未来如需集团、加盟或代运营，增加显式的租户关系、授权委托和审计记录；不得把普通部门层级偷偷当成租户关系。

默认登录链路固定为：

```text
Credential -> Account -> 选择 Tenant -> TenantMember -> 进入业务
```

一个账号只有一个全局身份，同一邮箱或手机号不能重复创建多个全局账号。账号可以通过多个 TenantMember 加入多个租户；只有一个可用租户时可以自动进入。租户专属域名可以提前限定候选租户，但不能绕过账号和成员校验。

平台操作员走独立的平台上下文和平台角色。它可以创建、停用租户和处理平台配置，但不能因为是平台操作员就自动获得租户业务数据权限。需要协助客户时，必须建立显式、限时、可审计的支持会话；该能力可在 P1 实现。

## 5. 模块、菜单和产品方案不是一回事

### 模块

模块是业务能力的真正所有者。例如库存模块负责库存台账、库存变动规则、查询接口、权限点和数据库迁移。

### 菜单

菜单只是用户进入页面的导航。菜单可以指向库存查询页面，但菜单不拥有库存逻辑，也不能代替后端权限校验。

### 产品方案

产品方案是一份装配清单。例如：

- 门店管理方案：门店、商品、库存、销售、收银、配送。
- 仓储管理方案：仓库、商品、库存、入库、出库、调拨、配送。

两个方案可以装配同一个库存模块，并展示不同菜单和页面。不是把库存模块复制两次，也不是在一个模块里“安装另一个模块”。

能力实际生效分三层：

1. 部署级已安装：这套部署中存在并加载了该 Module。
2. 租户级已开通：`TenantModule` 允许该租户使用，并保存租户级模块配置。
3. 成员级有权限：TenantMember 的角色和数据权限允许使用具体功能和数据。

三层必须同时满足。ProductProfile 只是批量初始化第二层和默认菜单的模板，不是最终授权依据。

## 6. 模块如何互相使用

在第一版模块化单体中，模块通过公开的服务接口或契约调用另一个模块。

例如：

```text
销售模块 -> InventoryService::decrease(...)
仓储出库模块 -> InventoryService::decrease(...)
调拨模块 -> InventoryService::transfer(...)
```

它们运行在同一个后端进程、可以使用同一个数据库，因此不需要为了“看起来先进”而先做网络微服务。但销售模块不得直接修改库存模块的表。

商品由商品模块维护，库存由库存模块维护。库存模块可以定义统一的“库存地点”概念，由门店或仓库关联到库存地点；销售、出库和调拨只把经过校验的库存地点交给库存服务。具体字段属于后续业务模块，不进入 Peanut Admin 核心表。

跨模块写操作由应用用例协调公开服务，并明确事务边界；事务提交后再发布事件。报表可以使用专门读模型，但不能反向修改模块真相数据。

### 门店和仓储共享库存的最小参考契约

这不是 Peanut Admin 的核心表设计，而是验证 Module 组合确实可落地的下游参考：

| 所有者 | 拥有的数据/规则 |
| --- | --- |
| 商品 Module | Product、SKU 和商品有效状态；对外提供 SKU 查询契约 |
| 库存 Module | StockLocation、StockBalance、StockLedger、库存增减和调拨规则 |
| 门店 Module | Store，并把需要存货的门店关联到一个或多个 StockLocation |
| 仓库 Module | Warehouse，并把仓库/库区关联到 StockLocation |
| 销售/出入库/调拨 Module | 自己的业务单据；通过库存公开命令改变库存 |

库存写入命令至少包含可信租户上下文、`idempotency_key`、SKU、来源/目标库存地点、数量、业务单据类型和业务单据 ID。库存 Module 校验地点与 SKU 状态，原子更新余额并追加不可覆盖的流水；调拨在同一事务中完成来源扣减和目标增加。

因此“门店管理系统”和“仓储管理系统”可以展示不同页面和流程，但不会各自维护一份库存余额。具体批次、库位、负库存和成本算法由库存产品设计决定，不由脚手架预设。

未来真的需要分开部署时，公开契约和数据所有权可以减少改造范围，但不能消除改造。API/事件、数据迁移、跨模块事务、读模型和一致性策略都必须重新设计。第一版不承诺“随时无成本拆成微服务”。

## 7. 数据隔离和数据权限

第一版默认共享数据库、共享表：

- 所有租户私有数据的 `tenant_id` 必须 `NOT NULL`，由服务端可信上下文写入，创建后不得修改。
- 不得用 `tenant_id = 0`、`NULL` 或特殊字符串表示平台管理方；平台数据和租户数据使用不同模型与守卫。
- 门店、仓库等对象范围的数据还要带相应对象标识，或使用统一的业务地点标识。
- 租户内业务唯一约束必须包含 `tenant_id`；租户内关联应使用包含 `tenant_id` 的复合约束，防止跨租户外键。
- 索引必须包含租户维度，但列顺序按真实查询、排序和选择性确定，不机械规定 `tenant_id` 永远排第一。
- 请求必须先解析租户上下文，再解析租户成员和权限。
- Account 只证明登录身份。租户 API 的有效访问主体必须同时包含状态有效的 Account、Tenant 和 TenantMember。
- 租户切换必须签发新的租户会话或上下文凭证，不能只接受前端临时修改的 `tenant_id`。
- 平台会话和租户会话必须使用不同的会话类型/audience 与授权守卫；平台凭证不能直接调用租户业务 API。
- ORM、原生 SQL、创建、更新、删除、聚合、批量、导入导出和后台任务必须执行同一租户守卫，不能只给列表查询加过滤器。
- 唯一约束必须包含正确的租户边界；不能只给业务编号建全局唯一索引。
- 缓存键、锁、幂等键、队列消息、定时任务、导出文件、文件元数据、对象存储路径、搜索索引和审计事件都必须携带并校验 Host/Tenant 范围。
- Worker 不得在缺少租户上下文时回退为平台权限。用户发起的异步任务执行时重新确认成员和权限；系统任务使用明确命名且限定租户的系统身份。
- 数据权限在租户隔离之后继续收窄，例如本人、本部门、部门及下级、指定门店、指定仓库或模块自定义范围。
- 平台管理方跨租户操作必须进入独立控制面，显式建立支持会话并记录操作方、目标租户、原因、时效和结果。

数据分为四类：

1. 全局共享数据：不属于租户，例如国家地区基础码表。
2. 租户私有数据：只需要 `tenant_id`，例如租户自己的商品目录。
3. 租户内对象数据：需要 `tenant_id` 和门店、仓库等范围，例如库存。
4. 跨租户协作数据：加盟、代运营、交易协作等，第一版不做通用模型，后续按明确合同和授权关系设计。

## 8. Application 和 Entry 的处理建议

旧方案中的 `Application`、`Entry`、`Portal`、`SystemInstance` 暂不作为第一版核心对象。

- 一个可独立构建的管理后台、POS 或小程序，直接称为客户端 `Client`。
- 一个供客户选择的“门店管理系统”或“仓储管理系统”，先用静态产品方案描述其模块装配。
- 路由和菜单负责页面入口，不额外建立 `Entry` 表。
- 部署实例由部署和运维系统管理，不进入业务授权主链。

如果后续出现必须由数据库动态管理多个品牌应用、域名、客户端版本和发布渠道的真实需求，再增加 `Application`，而不是提前让每个请求都携带一个难以解释的应用上下文。

## 9. 旧仓库处理建议

不建议直接把旧 `base-framework` 仓库改名后公开。

原因：旧 Git 历史包含多轮已废弃模型、DCS/Finance 示例和被删除的运行时代码，公开后会让贡献者误判事实源，也可能暴露不应成为公共框架历史的内部探索。

推荐做法：

1. 将旧仓库保留为本地只读的 `base-framework-legacy`。
2. 在 `/Users/xing/Documents/company-os/repositories/peanut-admin/` 使用独立、干净的 Git 历史。
3. 只复制用户确认后的文档、许可证、工程规则和经过复审的可复用代码。
4. 新仓库在运行时编码前先完成最小架构、功能范围、包边界和验收标准。

## 10. 当前结论

Peanut Admin 不是“每个模块各自做一套 SaaS”，而是“一套统一租户、账号、成员和权限底座，多个业务模块共同遵守租户隔离”。

门店和仓库是租户管理的业务对象；门店管理系统和仓储管理系统是不同的产品组合或客户端体验；商品、库存等模块是可被这些组合共同使用的业务能力。

该结论仍需用户在 `32-decision-confirmation-list.md` 中逐项确认。
