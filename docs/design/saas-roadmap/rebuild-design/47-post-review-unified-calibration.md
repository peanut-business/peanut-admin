## 1. 先用自然语言给出结论

Peanut Admin 不是“一个租户只能管理一种东西”的 SaaS 模板。

一个 Tenant 表示一个使用系统并承担账号、成员、组织、权限、配置和数据责任的经营组织。一个 Tenant 内可以同时存在多个类别、多个数量的业务主体或业务对象，例如：

- 多个门店；
- 多个仓库；
- 多个供应商；
- 多个批发商；
- 多个配送中心、销售渠道或以后由业务 Module 定义的其他对象。

一个成员也不是只能管理一个门店。一个 TenantMember 可以按授权同时管理同一类别中的一个或多个业务目标，例如门店 A、门店 B 和门店 C；还可以在另一项权限中管理仓库 W1 和 W2。

但“可以管理多个目标”不等于每一次操作都可以不说明目标。普通写操作仍应明确写入哪个门店、仓库或其他业务目标；跨多个目标的批量写入必须是单独设计、单独授权、单独审计的业务能力。

因此，Peanut Admin 的通用抽象应是：

```text
平台
└── Tenant（经营组织和 SaaS 隔离边界）
    ├── TenantMember / Department / Role（谁在这个 Tenant 中工作）
    ├── 已开通的 Module（这个 Tenant 可以使用哪些能力）
    └── Module 自己管理的业务主体或业务对象
        ├── Store：门店 A、门店 B、门店 C
        ├── Warehouse：仓库 W1、仓库 W2
        ├── Supplier：供应商 S1、供应商 S2
        └── 其他业务类型及实例

TenantMember + 功能权限 + 数据权限
        └── 决定某个成员对哪些类别、哪些具体目标、哪些操作有权
```

对话中偶尔使用的“主题”统一按“业务主体或业务对象”理解，不建立名为 `Subject` 的万能 Kernel 表，也不让底座猜测门店、仓库和供应商的具体业务字段。

## 2. 五层边界

### 2.1 平台控制面

平台控制面负责 Peanut Admin 实例自身的治理：

- 创建、开通、暂停、恢复和关闭 Tenant；
- 配置套餐、许可证和可开通 Module；
- 查看平台级运行状态和治理审计；
- 管理 PlatformOperator。

PlatformOperator 不是“天然能看全部租户业务数据的超级员工”。平台治理权限不能自动转化为商品、库存、订单等租户业务权限。

禁止用固定 `tenant_id = 1`、`tenant_id = 0` 或 `tenant_id IS NULL` 表示平台控制面。平台身份、平台会话、平台 API 和租户身份、租户会话、租户 API 必须分开。

### 2.2 Tenant

Tenant 是经营组织、客户或团队在系统中的 SaaS 责任边界，承担：

- 成员和部门边界；
- 功能开通和配置边界；
- 默认的数据隔离边界；
- 授权、审计和生命周期责任。

Tenant 不是门店、仓库、供应商、部门或 Module。即使一个简单项目只有一家公司和一家门店，仍然表达为“一个 Tenant + 一个 Store”，不能把 Store 记录直接当 Tenant。

### 2.3 Tenant 内的通用组织与成员

Peanut Admin Kernel 管理：

- `TenantMember`：某个 Account 在某个 Tenant 中的工作成员身份；
- `Department`：Tenant 内用于人员归属、组织管理和数据权限计算的组织结构；
- `Role` 和功能权限：成员可以使用哪些功能；
- 数据权限策略：成员可以操作哪些数据目标。

Department 不用于冒充门店、仓库或供应商。部门是人的组织结构，业务对象由相应 Module 管理。

一个 Account 可以在多个 Tenant 中分别拥有 TenantMember；同一个 TenantMember 不应因为可管理三家门店而复制成三条成员身份。

### 2.4 Module 拥有的业务主体和业务对象

门店、仓库、供应商、批发商等不是 Kernel 固定表，而是由业务 Module 定义、存储和维护。

每个 Module 必须明确：

- 它拥有哪些业务对象和事实；
- 每个对象的 Tenant 归属或其他所有权口径；
- 哪些对象可以成为数据权限目标；
- 如何根据授权生成查询条件；
- 如何校验单对象读写；
- 如何通过公开接口供其他 Module 使用。

底座提供 Module contract、权限扩展点和安全守卫，不提供 DCS 的 Store、Warehouse、Supplier 等具体表。

### 2.5 成员的数据目标范围

功能权限回答“能不能使用商品管理、库存查看、门店编辑等功能”。数据权限回答“可以对哪些门店、仓库或其他目标执行这项功能”。两者缺一不可。

一个成员可以得到如下授权结果：

```text
商品查看：Store {A, B, C}
门店编辑：Store {A}
库存查看：Warehouse {W1, W2}
库存调整：Warehouse {W1}
供应商查看：Supplier {S1, S2, S3}
```

授权结果必须按“资源 + 操作 + 目标类别”计算，不能把“当前成员可管理的全部门店”做成一个对所有 API 永远相同的全局列表。

## 3. 一个 Tenant 可以有多类别、多实例

“一个 Tenant 多门店”只是例子，不是完整模型。准确表述是：

> 一个 Tenant 可以拥有、管理或按业务关系使用多个类别的业务主体或业务对象；每个类别都可以有零个、一个或多个实例。

例如一个 DCS 经营组织可以同时管理：

| 类别 | 示例数量 | 业务含义 |
| --- | ---: | --- |
| 门店 | 12 | 销售、收银、门店库存和门店运营 |
| 仓库 | 2 | 仓储、补货、配送和批次库存 |
| 供应商 | 80 | 采购来源、合同和结算关系 |
| 批发客户 | 30 | 批发销售、价格和授信关系 |
| 配送中心 | 1 | 配送计划和履约组织 |

这里的 Supplier 可能只是当前 Tenant 维护的外部合作方记录，也可能未来对应另一个 Tenant。两者不能仅凭同名自动合并。若两个 Tenant 之间发生供应、加盟或代运营关系，必须由业务 Module 建立明确关系和授权。

简单项目可以只开一个 Tenant、一个 Module 和一个业务目标；复杂项目可以在同一套安全内核上开多个 Module 和多个目标。复杂度由业务配置和数据产生，不靠建立两套底座产生。

## 4. 一个成员可以管理多个同类目标

### 4.1 固定规则

Peanut Admin 必须支持：

1. 成员只管理一个门店；
2. 成员同时管理多个门店；
3. 成员只管理一个仓库；
4. 成员同时管理多个仓库；
5. 成员跨类别拥有不同范围，例如管理门店 A/B，同时只查看仓库 W1；
6. 同一成员对同一目标拥有不同操作范围，例如能看门店 A/B/C，但只能修改门店 A。

这不是 Tenant 的“单目标模式/多目标模式”开关，而是每个成员、角色、资源和操作的授权结果。

### 4.2 不建立全局 CurrentSubject

TenantContext 只证明当前进入哪个 Tenant、使用哪个 TenantMember 和哪一个可信会话。它不能额外固定一个对全部 Module 都有效的 `current_subject_id`，原因是：

- 门店和仓库不是同一类别，ID 无法安全混用；
- 一个页面可能同时读取多个门店并读取一个仓库；
- 成员对不同资源的目标集合不同；
- 全局目标容易被开发者误当成已经完成数据权限校验。

具体页面可以保存“当前选择的门店”作为界面状态，但后端仍必须按当前资源、操作和目标重新授权，不能信任前端选择值。

### 4.3 Module 自己的成员关系

如果业务本身需要记录店长、库管员、供应商联系人等关系，Module 可以维护自己的业务关系表。这类关系描述业务事实，不取代 Kernel 的 TenantMember、Role 和数据权限，也不能自动授予系统访问权。

## 5. 单目标、多目标与读写规则

### 5.1 操作基数

受保护资源应显式声明操作所允许的目标基数。候选口径如下，具体 schema 和接口仍由 G-03 至 G-05 校准：

| 基数 | 含义 | 默认行为 |
| --- | --- | --- |
| `one_required` | 一次命令必须明确一个目标 | 普通新增、修改、删除、入库、调拨等写操作采用 |
| `many_readable` | 可读取授权集合中的一个或多个目标 | 列表、查询和对比采用 |
| `aggregate_read` | 对多个目标读取聚合结果 | 报表使用，默认只读 |
| `policy_publish` | 将一份策略发布到多个目标 | 单独建模发布任务、结果和审计 |
| `bulk_write` | 一次修改多个目标的业务事实 | 默认关闭；有真实需求时单独设计和授权 |

“一个成员能管理多个门店”与“每次写操作只写一个门店”并不冲突。前者是长期授权集合，后者是单次命令边界。

### 5.2 推荐交互

| 可用目标数量 | 页面行为 |
| ---: | --- |
| 0 | 拒绝进入或显示无可用数据，不允许靠手填 ID 访问 |
| 1 | 可自动选择并隐藏切换器；列表可按需要隐藏归属列 |
| 多个 | 显示目标选择/筛选器；跨目标列表应显示归属列 |

多目标报表可以默认展示汇总和对比；进入修改动作时必须明确目标。界面隐藏目标列只是显示优化，不改变后端授权条件。

### 5.3 性能原则

多目标授权不是必然的性能瓶颈。实现时按目标集合大小选择成熟查询方式：

- 单目标使用等值条件；
- 小集合使用参数化 `IN`；
- 大集合使用授权关系表、`EXISTS`、临时授权投影或预计算读模型；
- 报表使用受控聚合读模型，不让页面循环请求每个目标；
- 缓存键必须包含 Tenant、成员、资源、操作、策略版本和必要的 Module 版本；
- 权限变化、成员停用、角色变化和目标关系变化必须使相关缓存失效。

任何性能优化都不能通过删除 Tenant 条件、跳过目标权限或开放通用 `disableTenantScope` 获得。

## 6. 全站共享、Tenant 数据与业务目标数据

### 6.1 先区分四种事实

| 数据性质 | 例子 | 所有权和隔离原则 |
| --- | --- | --- |
| 平台治理事实 | Tenant 生命周期、套餐、许可证 | 平台控制面拥有，不是租户业务表 |
| 统一共享主档 | DCS 的统一 Product/SKU 主档 | 由业务 Module 明确创建者、归属者、维护者和作用范围 |
| Tenant 私有事实 | Tenant 配置、成员、角色 | `tenant_id` 必填并强制隔离 |
| 业务目标事实 | 门店库存、仓库库存、门店销售 | 同时保留 Tenant 边界和明确业务目标归属 |

禁止在普通 Tenant 表中使用 `tenant_id = null` 表示“全站共享”。共享主档必须有自己的明确模型和作用范围。

### 6.2 DCS 商品采购例子

DCS 已确认商品中心是一套统一主档底座，不是“平台商品表 + 门店自采商品表”两套真相源。平台创建的商品、门店自采商品和未来其他主体创建的商品可以共用 Product/SKU 标识，差异通过以下事实表达：

- 创建主体；
- 归属主体；
- 维护主体；
- 可见范围；
- 采购范围；
- 销售范围；
- 库存范围。

门店采购时的推荐流程是：

1. 在统一 Product/SKU 查询服务中搜索可被当前门店采购或引用的商品；
2. 已存在匹配 SKU 时，选择同一个 `sku_id`，再建立门店的采购、经营或库存作用关系；
3. 不存在时，由有权成员在统一主档中创建门店归属 Product/SKU；
4. 新商品初始作用范围可以只覆盖该门店，不会因此变成第二套“门店商品池”；
5. 采购单、入库、库存批次和销售继续引用同一个 `sku_id`。

业务查询可以在数据库内部使用 `JOIN`、`EXISTS`、索引和读模型，但对外必须表现为一个统一候选集，不能要求页面把两个商品表 `UNION` 后再猜哪个 ID 是真相。

这一例子只用于证明底座必须提供“共享主档 + 所有权/作用范围”的扩展契约。Peanut Admin 不实现 Product、SKU、采购或库存业务。

## 7. 平台治理、代运营与跨 Tenant 合作

### 7.1 平台治理不是业务代管

平台团队可以治理 Tenant 账号、状态、Module 和许可证，但默认不能查看或修改 Tenant 的商品、库存、订单等业务事实。平台控制面不需要 Tenant 的业务授权，因为它根本不进入租户业务 API。

### 7.2 代运营必须是独立能力

代运营、客服支持或官方协助需要独立会话和授权流程，至少包含：

- 明确目标 Tenant；
- 明确委托方、受托方和有效期；
- 明确允许的功能和数据范围；
- 可撤销、可追溯；
- 显著标识当前正在代操作；
- 审计同时记录实际操作方和目标 Tenant。

P0 默认不实现代运营，也不允许 PlatformOperator 通过普通租户 API 绕过授权。

### 7.3 加盟和跨 Tenant 管理

未来可能出现总部 Tenant 需要查看或管理加盟门店，而门店业务归属于另一个 Tenant。此时需要 DCS 或专门协作 Module 建立跨 Tenant 的合同关系、资源关系和授权，不应把双方强行合并到一个 Tenant，也不能让组织层级自动产生权限继承。

P0 对跨 Tenant 业务访问默认拒绝。未来扩展时，审计合同至少要能区分：

- 实际 Account 和 TenantMember；
- 操作方 Tenant；
- 目标资源所属 Tenant；
- 目标业务主体或对象；
- 委托、加盟或协作关系/授权 ID；
- 使用的功能权限和数据权限依据。

## 8. Module、Client 和产品装配

### 8.1 同一套 Module 服务多个目标

商品、库存等 Module 在部署中安装一次，在 Tenant 中按能力开通，不为门店 A、门店 B、仓库 W1 分别复制代码或安装一套 Module。

Module 的服务根据明确目标和授权处理多个实例：

- 门店和仓库都可以使用商品主档能力；
- 门店库存和仓库库存可以复用库存领域契约，但归属目标和业务流程由 Module 明确；
- Store Admin、Warehouse Admin、POS、小程序等 Client 可以呈现不同菜单和页面；
- Client 的差异不应复制商品、库存等事实源。

### 8.2 跨 Module 使用

菜单可以直接指向某个 Module 贡献的页面；另一个 Module 需要业务能力时，应调用提供方的公开命令、查询或事件契约。禁止通过跨 Module 直接写表来复用功能，也不能因为两个 Client 都显示库存就复制两套库存真相。

### 8.3 跨目标报表

跨门店、跨仓库报表可以作为同一 Module 的只读查询能力，也可以在规模扩大后成为独立 Reporting Module 或读模型。它默认只读，不因为能汇总多个目标就自动获得跨目标修改权限。

## 9. 仓库、P0/P1 和升级边界

### 9.1 仓库和代码包

第一阶段仍采用一个公开 monorepo：`peanut-opensource/peanut-admin`。计划包含：

- `backend/`：ThinkPHP 8 参考后端和装配层；
- `frontend/`：Vue 3 + Vite + Element Plus Admin Shell；
- `packages/php/`：可复用后端核心包；
- `packages/web/`：可复用前端核心包；
- `templates/`：新项目脚手架模板；
- `docs/`、`scripts/`、`examples/`：文档、工程工具和受控示例。

DCS、Finance Manager、门店经营、仓储作业和运营平台的业务代码不得进入 Peanut Admin。

### 9.2 P0 与 P1

P0 证明以下最小闭环能够安全工作：

- 账号凭证登录；
- 选择 Tenant 并建立 TenantMember 会话；
- 部门、角色、功能权限和数据权限；
- TenantModule 与 Module 扩展契约；
- 一个不含 DCS 业务的多目标权限示例；
- 审计、测试、迁移、文档和工程门禁。

P0 完成后是可继续开发的内部 alpha 底座，不冒充成熟 LikeAdmin 成品。P1 再补成普通开发者可以开箱使用的管理后台，包括更完整的系统管理、文件、任务、消息、导入导出、备份恢复和发布体验。

### 9.3 升级不是覆盖项目代码

后续升级分层处理：

- Composer/npm 核心包按语义化版本升级；
- 数据结构由可审计 migration 升级；
- 脚手架生成后的业务代码不由上游直接覆盖；
- Admin Shell 和模板通过版本清单、升级说明、兼容检查和必要的 codemod 演进；
- 项目版本、授权和升级治理由后续独立主控端处理，不提前塞进 P0 Kernel。

## 10. 已确认与仍需详细设计

### 10.1 本轮已确认

1. Tenant 是经营组织和 SaaS 隔离边界，不是门店或仓库。
2. 一个 Tenant 可以有多个类别、每类多个业务主体或业务对象。
3. TenantMember 可以同时管理多个同类别目标，也可以在多个类别中拥有不同范围。
4. 多目标能力由功能权限和数据权限共同决定，不靠复制成员身份。
5. 普通写操作明确一个目标；跨目标写入必须单独建模和授权。
6. TenantContext 不建立对全部 Module 通用的 CurrentSubject。
7. 平台治理、代运营和跨 Tenant 业务合作是三种不同能力。
8. 平台默认不能访问租户业务，跨 Tenant 业务在 P0 默认拒绝。
9. 统一共享主档使用一个事实源，通过归属和作用范围区分，不拆两套真相池。
10. Peanut Admin 提供通用扩展契约，不实现 DCS 业务对象。
