# Peanut Admin 决策确认清单

> 状态：Accepted（2026-07-15）
>
> 用户已明确确认 A-D 四组推荐方案，对应 D-01 至 D-16。该确认只允许进入字段级设计，不等于授权编写运行时代码。
>
> 47 号文档对多类别业务目标、多目标授权和共享主档作了后续校准；冲突时以 47 号为准。

编码前架构决策：D-01 至 D-10、D-12、D-13、D-15、D-16。

公开发布决策：D-11、D-14。它们不阻塞本地字段级设计，但必须在创建/发布公共包前完成。

## D-01 是否从干净仓库重新开始

**推荐：是。**

- 旧 `/base-framework` 改为本地 `base-framework-legacy`，只读保留。
- 新建 `/peanut-admin` 和干净 Git 历史。
- 只迁移最终确认的文档、规则和经过复审的代码。

效果：避免公开仓历史充满已废弃 V2/V3/V4、内部业务例子和问题代码。代价是不能直接沿用旧提交历史，但旧仓仍可追溯。

## D-02 公开仓库拆分

**推荐：第一阶段一个公开 monorepo，但内部保留四个清晰项目边界。**

`peanut-admin` 同时包含 `backend/`、`frontend/`、`packages/php/` 和 `packages/web/`。核心包拥有独立 manifest 和 public API，P0 用 workspace/path dependency，P1 可从 monorepo 发布 Composer/npm 包。

至少有两个真实消费者、API 连续两个发布周期稳定，或维护/发布节奏明显分开后，再评估拆成 `peanut-admin-php`、`peanut-admin-web`。私有业务项目不放入 `peanut-opensource`。

## D-03 唯一租户根

**推荐：统一使用 Tenant，不用 Organization 代表同一层。**

Tenant 是经营组织、签约和数据隔离边界；Department 是租户内部组织结构；Store、Warehouse、Supplier 等是租户管理或发生业务关系的对象。

效果：避免“租户和组织是不是同一个”的长期混淆。表名可使用 `tenant`、`tenant_member`，不需要缩写冗长的 `organization`。

## D-04 一个租户管理多个对象

**推荐：支持。**

一个租户可同时管理多个类别、每类多个业务对象，例如多个门店、仓库、供应商和批发商。成员先获得租户身份，再由功能权限和数据权限决定可以对哪些类别中的哪些具体目标执行哪些操作；同一成员可以同时管理多个同类目标。

即使只有一家独立签约的门店，Tenant 仍表示经营该门店的公司或团队，门店仍是 Tenant 内的业务对象。不能把 Store/Warehouse 记录直接提升为 Tenant，也不能仅因为对象类型建立租户。

## D-05 门店管理和仓储管理的定位

**推荐：它们是两个产品方案/客户端体验，不是两个不可共享数据的租户体系。**

门店方案和仓储方案可以分别部署前端，也可以装在同一套后台；两者复用商品、库存等模块和统一数据库。业务操作都经过模块服务契约。

效果：用户看到独立系统，底层仍只有一份商品和库存事实。

## D-06 Module 的定义

**推荐：Module 是业务能力所有权边界，不是菜单目录。**

Module 拥有自己的规则、数据表、API、权限、迁移和服务契约。菜单只指向页面，角色决定是否可见/可操作。

模块间调用公开服务；同一模块化单体内是进程内调用，未来拆服务时再适配为 API/事件。

模块能力按“部署已安装 -> 租户已开通 TenantModule -> 成员有权限”三层生效。产品方案只负责初始化开通项，不直接替代授权。

## D-07 ProductProfile、Application 和 Entry

**推荐：P0 保留静态 ProductProfile，暂不建立 Application、Entry、Portal、SystemInstance 核心表。**

- ProductProfile 描述某产品装配哪些模块和菜单。
- Client 表示真正构建的 Admin、POS、移动端或小程序。
- 菜单和路由完成页面入口。

效果：保留“门店系统/仓储系统”的产品概念，又不让每个请求经过无法解释的 Application/Entry。出现动态多品牌、域名、发布渠道管理需求后再增加 Application。

## D-08 数据库和租户隔离

**推荐：P0 使用共享数据库、共享表和强制 `tenant_id`。**

租户私有查询由后端上下文自动过滤；对象范围再叠加门店/仓库标识和数据权限。Host 跨租户操作走独立控制面并审计。

`tenant_id` 必须非空、由可信上下文写入且不可修改；查询、写入、原生 SQL、批量、导出和后台任务使用同一守卫。平台会话与租户会话分开，平台凭证不能直接调用租户 API。

独立数据库作为未来部署策略，不进入 P0。禁止默认使用每租户一组表。

## D-09 数据权限

**推荐：P0 同时完成组织范围和业务对象范围。**

基础范围包括本人、本部门、部门及下级、全部和指定部门；模块可贡献指定门店、指定仓库等授权对象与查询 Provider。没有匹配规则时默认拒绝。

只做菜单/RBAC 而没有后端数据权限，不算 P0 完成。

规则存储至少要表达角色、资源、动作、条件组和指定目标。租户守卫永远先执行；单条规则内条件取交集，多条有效规则/角色取并集。具体表字段、Provider 接口和列表/详情/写入/批量/异步算法必须在 `33-pre-code-design-gates.md` 的 G-03 完成后才能编码。

## D-10 Plugin 的优先级

**推荐：P0 定义 Module 契约，P1 再实现 Plugin 安装、升级、卸载。**

这样 P0 已能开发和装配模块，但不会在核心模型尚未稳定时先做复杂应用市场。插件市场、签名分发和商业授权放到 P1/P2。

## D-11 开源与私有仓托管

**推荐：公开脚手架和核心包放 GitHub `peanut-opensource`；company-os 和私有业务仓继续使用 Gitee 私有仓。**

未来若 GitHub 私有协作、Actions 或海外生态有明确优势，可以把部分私有仓迁到单独的私有组织；不要把客户/商业项目混入开源组织。

## D-12 第一版范围

**推荐：把 P0 定义为安全可运行内核，不把整个成熟后台压进第一个里程碑。**

P0 只完成安装/迁移、邮箱密码登录、Tenant/TenantMember、平台操作员、租户切换、RBAC、最小部门与对象数据权限、强制隔离、Module/TenantModule、审计、最小 Admin Shell 和安装升级测试。P1 补成市场可用后台，P2 再做生态和运营能力。

P1/P2 只保留边界和扩展点，不允许低上下文 Agent 擅自提前实现。商品、库存、门店、仓储、Finance 和 DCS 业务不进入底座。

## D-13 旧计划状态

**推荐：旧 base-framework V2/V3/V4 和 R-00/R-01/R-02 全部标记为历史，不续跑。**

新方案确认后重新生成 Peanut Admin 的 P0 计划。旧代码只能逐项审查后引用，不能因为“已经写过”就自动迁移。

## D-14 尚需名称核验

**推荐：架构确认后、创建远程仓前统一核验。**

需核验：

- 当前 GitHub 仓库名 `peanut-admin`。
- 未来确需分仓时，候选 `peanut-admin-php`、`peanut-admin-web` 另行核验，不提前占位。
- Packagist vendor 和 Composer 包名。
- npm scope `@peanut-admin/*` 或其他可用名称。
- 中文展示名“花生后台框架”及主品牌“花生”的商标风险。

在可用性和商标检查完成前，包名只视为候选，不写进不可逆的公共 API。

## D-15 登录身份链路和平台操作员

**推荐：固定使用全局账号、多租户成员和独立平台操作员。**

标准业务登录链路是 `Credential -> Account -> Tenant -> TenantMember`。邮箱和手机号作为全局唯一凭证，一个 Account 可通过多个 TenantMember 加入多个 Tenant。

平台操作员使用平台角色管理租户和平台配置，不自动成为任何租户成员，也不能静默查询租户业务数据。后续支持客户时使用限时、显式、完整审计的支持会话。

## D-16 逻辑数据平面和未来拆分承诺

**推荐：P0 区分平台控制数据、全局身份数据和租户业务数据的所有权，但不提前建设微服务。**

租户业务模块不能直接读取平台操作员数据，平台控制面也不能任意 JOIN 租户业务表。TenantMember 是全局 Account 与 Tenant 的受控关联，由身份/成员服务提供。

模块契约和数据所有权只能降低未来独立部署的改造范围，不能承诺无成本替换为 API/事件。独立数据库、跨服务事务、数据迁移和最终一致性延后单独设计。
