# 能力状态与验收 Gate

能力账本使用以下固定状态，禁止用“差不多完成”“基本可用”代替：

| 状态 | 含义 | 最低要求 |
|---|---|---|
| `planned` | 已决定要做，尚未开始 | 有明确能力边界和验收条件 |
| `in_progress` | 已有 owner 或候选正在推进 | 不得引用为可消费能力 |
| `implemented` | 实现已经形成，但真实验收尚缺 | 明确列出尚缺 Gate |
| `verified` | 固定候选满足本能力全部验收条件 | 至少一个稳定证据引用 |
| `blocked` | 缺少明确输入或外部条件 | 必须记录精确 blocker 与解除条件 |
| `deferred` | 经决定暂缓 | 必须记录原因和恢复条件 |
| `out_of_scope` | 不属于本产品或当前授权边界 | 必须说明归属或重新立项条件 |
| `retired` | 能力或合同已退出 | 保留历史身份并指向替代项 |

## 完成层级

以下结论不能混用：

1. **实现完成**：代码或合同已经形成。
2. **能力已验证**：该能力自己的验收条件在固定候选上通过。
3. **交付合格**：所有直接依赖能力与组合 Gate 通过。
4. **发布就绪**：发布身份、制品、环境和恢复条件全部固定。
5. **已发布**：Tag、Release、部署及发布后最低 smoke 均有事实证据。

例如，create-app 的确定性测试通过，可以使“创建独立应用”能力成为 `verified`；但在新生成
应用上尚未完成依赖安装、数据库、服务和浏览器组合 Gate 时，整体交付仍只能是
`in_progress`。

## 状态变化规则

- 功能 PR 可以把能力推进到 `implemented`，但不得用未结束 CI 或开放 PR证明 `verified`。
- `verified` 的证据必须绑定完整 commit、不可变 Release、已完成 CI run 或仓库内固定报告。
- 验收失败时，只更新为 `blocked` 或保留当前状态并记录尚缺 Gate；不得删减原验收条件来
  获得绿色状态。
- 状态变化与相关代码在同一 PR 更新；如运行时证据只能在合入后取得，由唯一文档 owner
  立即提交一个纯文档 follow-up。
- 每项能力只描述稳定边界。临时日志、每次 CI 状态变化和会话交接不进入账本。
